# Observability MCP ecosystem: build our own tools or use existing MCP servers?

- **Ticket:** [#6](https://github.com/itsankoff/incident-copilot/issues/6), part of map [#3](https://github.com/itsankoff/incident-copilot/issues/3)
- **Date:** 2026-10-17. Stars, release, and activity figures come from the GitHub API on that date.
- **Constraints checked against:** [ADR 0001](../adr/0001-autonomy-and-trust-model.md), invariant 3 (*read and write are separated: investigation tools are read-only, only the executor holds write credentials*) and invariant 7 (*secrets never reach the LLM or the audit log*).

## Answer

Every backend on the list now has at least one MCP server from its vendor or project. Prometheus, Grafana, Kubernetes, AWS, Azure, and Google all ship servers written by their own teams. Datadog offers only a hosted (SaaS) server. Loki has no maintained standalone server: it is reached through `mcp-grafana` or the `kubernetes-mcp-server` logs toolset. Four of the servers are written in Go on the same official `modelcontextprotocol/go-sdk` v1.8.0 that incident-copilot would use.

incident-copilot can use these servers as an MCP client without weakening invariants 3 and 7, under four conditions:

1. **The boundary is the server's credentials, not its flags.** A server's `--read-only` flag hides tools. It does not remove the power to write. Azure's own AKS server documentation calls its access level "a guardrail to reduce accidental damage… not a security boundary". Each server must run with read-only credentials: a Kubernetes ServiceAccount with only `get`, `list`, and `watch` and no Secrets, a Grafana Viewer service account scoped to `datasources:query`, read-only IAM, or a Datadog service account without `mcp_write`. That keeps invariant 3 true even if a flag is wrong.
2. **The agent keeps its own tool allowlist.** The agent passes the LLM only tool names it has listed. Tool annotations such as `readOnlyHint` are hints, and clients must treat them as untrusted (MCP spec).
3. **The agent redacts every tool result before it reaches the LLM or the audit log.** No third-party server runs our redactor, but incident-copilot is the MCP client, so every result passes through its own Go code first.
4. **Reject any server whose tool arguments accept a URL or a credential.** `grafana/loki-mcp` does both, so the model, or text injected into a log line, could send the server's credentials to an address of its choosing. That breaks invariant 7.

**Recommendation for v1 (Kubernetes first):** keep our own six purpose-built tools for Prometheus, Loki, and the Kubernetes API, as the README plans. Reasons:

- They are incident-shaped. They take scope from the alert's labels, have fixed output budgets, and give the eval harness deterministic output.
- The generic servers each expose 30 to 100+ tools, so the allowlist and RBAC work would be about the size of the tools themselves.

Design the investigation-tool seam as **"MCP client + allowlist + redaction"** so that one tool can be served either in-process or by an external MCP server. For the cloud backends (CloudWatch, Azure Monitor, Google Cloud Observability, Datadog), use the vendor servers through that seam rather than writing our own: each has a read-only path and is maintained by the vendor. The candidates to adopt first are `prometheus/prometheus-mcp`, `grafana/mcp-grafana`, and `containers/kubernetes-mcp-server`. All three are Go, on go-sdk, and actively maintained.

## How each invariant maps to an external server

### Invariant 3: read and write are separated

- **What holds:** each external server runs as its own process. That is either a stdio subprocess (go-sdk `mcp.CommandTransport`) or a sidecar or Deployment reached over streamable HTTP (`mcp.StreamableClientTransport`; see [go-sdk](https://github.com/modelcontextprotocol/go-sdk)). It is part of the **agent** role and gets only credentials that can read. The executor never talks to any MCP server.
- **What does not hold by itself:** flags. Some servers expose writes by default: Prometheus `quit` and `reload`, Grafana dashboard and alert writes, Datadog `workflows`, `code-exec`, and `remote-actions`, Flux159 `kubectl_apply`. Others wrap a CLI that can do anything the server's identity can (`aks-mcp`, `gcloud-mcp`'s `run_gcloud_command`). The [AKS MCP README](https://github.com/Azure/aks-mcp#what---access-level-is-and-is-not) states the general rule: whoever can call the server holds the server identity's full privileges. So invariant 3 depends on the **credential**:
  - **Kubernetes:** the ADR's agent RBAC (`get`, `list`, `watch`), with Secrets excluded by RBAC and not only by `denied_resources`.
  - **Grafana:** a Viewer service account limited to named datasources.
  - **Prometheus:** a backend without `--web.enable-lifecycle` or the admin API (both off by default in Prometheus). Prometheus has no authorization of its own, so this is the only lever.
  - **Clouds:** read-only IAM or RBAC roles, a GCP IAM deny policy on non-read-only tools, and a Datadog key without `mcp_write` plus the org write switch turned off.
- **Defense in depth on top:** use the server's read-only flag and allowlist, *and* a client-side allowlist in the agent. Per the [MCP tools spec](https://modelcontextprotocol.io/specification/2025-06-18/server/tools), clients must treat `readOnlyHint` and the other annotations as untrusted unless the server is trusted, so our allowlist names tools explicitly.

### Invariant 7: secrets never reach the LLM or the audit log

- **Backend credentials** stay in the server process (env, file, or workload identity) and never enter a tool argument or result, with three exceptions to avoid:
  - Servers whose tool schemas take credentials or target URLs as arguments: [`grafana/loki-mcp`](https://github.com/grafana/loki-mcp/blob/main/internal/handlers/loki.go) accepts `url`, `username`, `password`, and `token`, and falls back to the env credentials for an LLM-chosen `url`. Excluded.
  - Tools that return credentials: `kubernetes-mcp-server` `configuration_view` (kubeconfig), Secret reads, and `pods_exec`. Disable all three and block Secrets in RBAC.
  - Grafana per-request `X-Grafana-URL` overrides: these are HTTP headers set by the client, not by the LLM, but leave them unconfigured.
- **Secrets inside observability data** (a token printed in a log line, an env value in a pod spec) are the same risk whether our tools or a third-party server fetch them. ADR 0001 D7 already requires redaction before the LLM and the audit log. Because incident-copilot is the MCP client, every `CallToolResult` passes through agent code, so the redactor runs there no matter which server produced the result. Server-side redaction (for example `kubernetes-mcp-server`'s redaction of MCP log messages) is a bonus, not the control.
- **Output budgets:** some size limits are arguments the model sets: Prometheus `truncation-limit` can be overridden per call, `loki-mcp` `limit` has no cap, Datadog has `max_tokens`. The agent should enforce its own byte budget on each result as well. This matters for cost and for limiting injected text, not for invariant 7 directly.

## Why not adopt them wholesale for v1

- **Shape:** an incident tool should take its scope from the Signal (namespace plus workload from the alert labels; ADR 0001 D3 scope binding) and return a small, fixed shape that the eval harness can score. Generic servers expose the whole API: `kubernetes-mcp-server` has dozens of tools across many toolsets, and `mcp-grafana` has 100+. The model gets more ways to wander, and every new tool needs an allowlist review.
- **Dependency and supply chain:** each server is another image to pin and another credential to issue. The Python and TypeScript servers add runtimes to the Install.
- **Small gap:** the six README tools are thin wrappers over the Prometheus, Loki, and Kubernetes clients, which incident-copilot needs anyway for Detectors and executor preconditions.

## Where existing servers clearly win

- **Cloud backends (post-v1):** CloudWatch, Azure Monitor (Log Analytics KQL, metrics, activity log), Google Cloud Logging, Monitoring, and Trace, and Datadog. Each vendor server is maintained alongside fast-moving APIs and has a read-only path: tool-level reads plus IAM. Writing our own means owning several cloud SDKs.
- **Operators who already run Grafana:** `mcp-grafana` with `--disable-write` reaches every datasource Grafana has (Prometheus, Loki, CloudWatch, Cloud Logging, Elasticsearch), and the datasource credentials never leave Grafana. That is a strong fit for invariant 7.
- **Third-party agents:** the README's goal that "any MCP-capable agent can use our tools" is not affected. Our own MCP server stays, and it can sit next to vendor servers in another agent's config.

## Open points for the M2 design

- Where the seam sits: an `investigation.Tool` interface implemented by in-process tools and by an MCP-client adapter (allowlist + redaction + byte budget), or a single in-process MCP client for everything.
- Whether external servers run as sidecars in the agent Pod or as separate Deployments. All containers in a Pod share one ServiceAccount, so only separate Deployments give each server its own credentials. This choice decides how fine-grained credential separation can be.
- `prometheus-mcp`, `mcp-grafana`, and `kubernetes-mcp-server` are Go modules on the same go-sdk. Whether their tool handlers can be imported as libraries rather than run as processes has **not been verified**.
