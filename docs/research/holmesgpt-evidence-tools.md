# Prior art: how HolmesGPT handles evidence tools

- **Ticket:** [#19](https://github.com/itsankoff/incident-copilot/issues/19), blocks [#10](https://github.com/itsankoff/incident-copilot/issues/10) (the evidence tool contract), part of map [#3](https://github.com/itsankoff/incident-copilot/issues/3)
- **Date:** 2026-10-18
- **Source version:** [robusta-dev/holmesgpt](https://github.com/robusta-dev/holmesgpt) at commit [`5feabfc`](https://github.com/robusta-dev/holmesgpt/tree/5feabfca750b) (2026-10-18, `master`). Latest release is 0.45.0 (2026-10-15). 3.6k stars, Apache-2.0. All file links below point at that commit. Docs are the `docs/` folder at the same commit, published at [holmesgpt.dev](https://holmesgpt.dev).
- **Constraints checked against:** [ADR 0001](../adr/0001-autonomy-and-trust-model.md) safety invariants 3 (read and write are separated), 4 (actions are bound to scope), 7 (secrets never reach the LLM or the audit log), and 8 (fail closed); the [CONTEXT.md](../../CONTEXT.md) topology (Control plane, Sensor, Executor, Location, Target).
- **Legend:** **[code]** means verified by reading the source at the commit above. **[docs]** means stated only in documentation. **[inferred]** means a conclusion drawn from the code that was not executed.

## Answer

HolmesGPT is a single process that runs the LLM loop **and** the tools, usually in the cluster it investigates. Its tools are mostly backend-specific: raw PromQL, raw LogQL, `kubectl get <kind> | jq`, and a free-form `bash` tool guarded by a prefix allowlist. Its read-only guarantee rests on credentials (a get/list/watch ClusterRole without Secrets), with the bash allowlist and a human approval prompt on top. It does **not** bind reads to the alerting workload, does **not** filter the catalog per investigation, does **not** redact tool output, and does **not** cite evidence or frame tool output as untrusted. Its output budgets are good and worth copying. Its cross-cluster mode is the closest prior art to our Sensor: a Holmes instance in another cluster runs exactly one tool per request, with no LLM loop, re-checks that the tool is exposed, and caps the result at 1 MB.

For incident-copilot, HolmesGPT mostly **confirms** the current direction (Q1 to Q7 below). It gives no reason to supersede ADR 0001 in a way that would weaken an invariant. It does show two places where ADR 0001's wording should be **tightened**, not relaxed: investigation tools should be typed queries with no shell (ADR 0001 only forbids shell for actions), and redaction must run before *any* LLM, including a summarizer model.

## Findings

### 1. Tool shape: toolsets, declaration, enablement

- **A toolset is a named group of tools with prerequisites, LLM instructions, tags, and config** ([`holmes/core/tools.py`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/holmes/core/tools.py) `class Toolset`). **[code]** Declared three ways:
  - **YAML:** each tool is a Jinja-templated shell `command` or `script`, run with `/bin/bash` after each parameter is `shlex.quote`d (`YAMLTool`, `sanitize_params`). Example: [`kubernetes.yaml`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/holmes/plugins/toolsets/kubernetes.yaml) (`kubernetes_jq_query`, `kubernetes_tabular_query`, `kubernetes_count`), [`kubernetes_logs.yaml`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/holmes/plugins/toolsets/kubernetes_logs.yaml) (`kubectl logs {{pod_name}} -n {{namespace}}`). Operators can write their own YAML toolsets (`docs/data-sources/custom-toolsets.md`).
  - **Python:** classes registered in [`holmes/plugins/toolsets/__init__.py`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/holmes/plugins/toolsets/__init__.py) `load_python_toolsets` (Prometheus, Loki, Datadog, Elasticsearch, bash, and about 25 others). Many are wrapped in `multi_instance(...)`, which adds an `instance` parameter so one toolset can point at several backends.
  - **MCP servers and HTTP APIs:** `mcp_servers:` entries become `RemoteMCPToolset`s ([`toolset_mcp.py`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/holmes/plugins/toolsets/mcp/toolset_mcp.py)). An HTTP toolset turns whitelisted REST endpoints into tools ([`http_toolset.py`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/holmes/plugins/toolsets/http/http_toolset.py)).
- **The tools are mostly backend-specific.** **[code]** `execute_prometheus_instant_query` and `execute_prometheus_range_query` take raw PromQL ([`prometheus.py`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/holmes/plugins/toolsets/prometheus/prometheus.py)). `grafana/loki` takes raw LogQL. `kubernetes_jq_query` takes a resource kind and a jq expression. `bash` takes any command string. The one capability-level tool is `fetch_pod_logs(namespace, pod_name, start_time, end_time, filter, exclude_filter, limit)` ([`logging_utils/logging_api.py`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/holmes/plugins/toolsets/logging_utils/logging_api.py)), which was designed to sit in front of several log backends.
- **Enablement is per installation, in config.** **[code]** The `Toolset.enabled` default is `False`. Built-ins such as `bash` and `kubernetes/core` ship enabled. Operators toggle toolsets under `toolsets:` in Helm values or `~/.holmes/config.yaml`. Tags (`core`, `cluster`, `cli`) select which toolsets the CLI and the server load ([`toolset_manager.py`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/holmes/core/toolset_manager.py) `_list_all_toolsets`).

### 2. Read scope

- **No binding to the alerting workload.** **[code]** No tool takes its scope from the alert. The model passes `namespace`, `pod_name`, or a PromQL selector of its choosing, and `kubernetes_jq_query` may omit the namespace entirely to list cluster-wide.
- **The real scope is the ServiceAccount.** **[code]** The chart grants a **ClusterRole** by default ([`holmesgpt-service-account.yaml`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/helm/holmes/templates/holmesgpt-service-account.yaml)). `namespaceScopedRBAC: true` renders the same rules as a namespaced Role instead ([`values.yaml`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/helm/holmes/values.yaml) line 91).
- **Namespace scope is also told to the model.** **[code]** `SCOPED_NAMESPACES` is rendered into the system prompt ("Never run cluster-wide queries…", [`generic_ask.jinja2`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/holmes/plugins/prompts/generic_ask.jinja2), [`prompt.py`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/holmes/core/prompt.py) `get_scoped_namespaces`). The prompt is advice only. RBAC is what enforces it.
- **Cross-cluster provenance is handled in the prompt.** **[code]** When `cluster_name` is set, the prompt tells the model that kubectl only sees that cluster, that external sources (Datadog, Loki) may hold other clusters' data, and that "every finding must carry its real cluster of origin".

### 3. Catalog ownership, filtering, prerequisites, health

- **The operator owns the catalog.** **[code]** It is built-ins plus config plus custom YAML plus MCP servers. It is the same for every investigation on that instance. No code filters it per alert or per Target. The only per-request change is the API caller injecting "frontend tools" ([`server.py`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/server.py) `inject_frontend_tools`).
- **Prerequisites decide whether a toolset loads.** **[code]** There are four kinds: a static flag, a shell command (`kubectl version --client`), required env vars, and a Python callable. Each toolset ends up `enabled`, `disabled`, or `failed` (`Toolset.check_prerequisites`). Checks time out after 20 s and the toolset is marked failed (`DEFAULT_TOOLSET_PREREQ_TIMEOUT_SECONDS`). Results are cached in `toolsets_status.json`, and the server re-checks them periodically (`status_refresh_interval_seconds`).
- **Failures are visible to the model.** **[code]** [`_toolsets_instructions.jinja2`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/holmes/plugins/prompts/_toolsets_instructions.jinja2) lists disabled and FAILED toolsets with their error, and tells the model to report a missing integration rather than guess.
- **MCP tool filtering and health.** **[code]** `allowed_tools` (fnmatch patterns) drops every other tool the server lists. `approval_required_tools` asks a human before a matching tool runs. `health_check_tool`, or an auto-detected `get_me` / `whoami`, is called with `{}` at startup to prove the credential works ([`remote-mcp-servers.md`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/docs/data-sources/remote-mcp-servers.md), `RemoteMCPToolset._filter_allowed_tools`).

### 4. MCP: client, server, restrictions

- **Client: yes.** **[code]** stdio, SSE, and streamable HTTP transports (`MCPMode`), OAuth, and per-request header propagation. MCP tool annotations (`readOnlyHint`, `destructiveHint`) are **ignored**: a grep of `holmes/` finds no use of them. Read-only behaviour is left to `allowed_tools` and the server's credentials.
- **Server: not in the open-source binary.** **[code]** `server.py` is a FastAPI app with no MCP endpoint. **[docs]** The **Robusta platform** (SaaS, closed source) hosts `/api/platform-mcp`, which lets any MCP client (Claude Code, Claude Desktop) run the fleet's cluster-local tools with a Robusta API key ([`cross-cluster-tools.md`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/docs/data-sources/cross-cluster-tools.md)). The restrictions are an account switch that is off by default (`expose_remote_tool_calls_externally`), a per-cluster RBAC permission (`MA_HOLMES_CHAT`), pre-approved tools only, and a 1 MB result cap.
- **The chart ships MCP servers as add-on pods.** **[code]** Pods for AWS, Azure, GCP, GitHub, Kubernetes, Sentry, and others ([`helm/holmes/templates/mcp-servers/`](https://github.com/robusta-dev/holmesgpt/tree/5feabfca750b/helm/holmes/templates/mcp-servers)). Each runs in its own Deployment, with its own ServiceAccount and optional NetworkPolicy.

### 5. Redaction and output budgets

- **No redaction of tool output.** **[code]** A grep for `redact`, `mask`, and `scrub` finds only two sites:
  - `ToolInvokeContext.model_dump` hides `request_context` (HTTP headers) in logs.
  - Datadog `sanitize_headers` hides API keys in request logging.

  Nothing scans tool results before they reach the LLM. Keeping secrets out relies on RBAC leaving out `secrets`, the documented advice to deny `kubectl get secret` in bash ([`bash.md`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/docs/data-sources/builtin-toolsets/bash.md)), and the system prompt's "never guess values you cannot see, like secrets".
- **Per-tool budget (verified).** **[code]** After each call, `spill_oversized_tool_result` ([`tool_context_window_limiter.py`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/holmes/core/tools_utils/tool_context_window_limiter.py)) counts tokens against `min(15% of the context window, 25,000 tokens)` (`TOOL_MAX_ALLOCATED_CONTEXT_WINDOW_PCT`, `TOOL_MAX_ALLOCATED_CONTEXT_WINDOW_TOKENS` in [`env_vars.py`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/holmes/common/env_vars.py); `LLM.get_max_token_count_for_single_tool`). An oversized result is written to disk and replaced by a preview plus "use `cat <file>` (pre-approved)". If no disk is available, the result is dropped with an error telling the model to narrow the query.
- **Per-backend limits.** **[code]**
  - Prometheus: metadata APIs are capped at 100 results with a "results truncated" note. Range queries are held to `MAX_GRAPH_POINTS` (500 by default; the model can raise it up to a hard limit). `query_response_size_limit_pct` sets a per-instance cap. Over-wide results come back with a `topk(5, …)` suggestion.
  - `fetch_pod_logs`: defaults to 100 entries and 7 days. `truncate_logs` cuts the *oldest* lines first, keeps lines whole, and prepends `[... PREVIOUS LOGS ABOVE THIS LINE HAVE BEEN TRUNCATED]`.
  - Every subprocess runs under `ulimit -v` (800 MB on x86) and gets an `[OOM]` hint back ([`tool-execution-safety.md`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/docs/data-sources/tool-execution-safety.md)).
- **Summarisation by a second LLM.** **[code]** The `llm_summarize` transformer sends raw `kubectl logs` output over 1,000 characters to a "fast model" for summary, and reverts if the summary is not smaller (`Tool._apply_transformers`, [`kubernetes_logs.yaml`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/holmes/plugins/toolsets/kubernetes_logs.yaml)).
- **Per-investigation budget.** **[code]** There is no byte cap. Before each LLM call, the conversation is compacted by an LLM summary once it nears a threshold of the context window ([`docs/reference/context-management.md`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/docs/reference/context-management.md), `holmes/core/truncation/compaction.py`). A call identical to an earlier one is refused ([`safeguards.py`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/holmes/core/safeguards.py); its comment notes this is only reasonable "if Holmes is read only").
- **Remote results.** **[code]** Capped at 1 MB uncompressed and gzipped above 100 KB. Oversized results fail with "narrow the query" (`REMOTE_TOOL_RESULT_MAX_BYTES`, [`tool_call_worker.py`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/holmes/core/conversations_worker/tool_call_worker.py) `serialize_tool_response`).

### 6. Read-only enforcement

- **Credentials first.** **[code]** The ClusterRole grants only `get` / `list` / `watch` on workloads, events, `pods/log`, nodes, RBAC objects, CRDs, Prometheus Operator CRDs, and opt-in operator CRDs (Argo, Flux, KEDA, Istio…). `secrets` is absent. `configmaps` **is** granted, and ConfigMaps sometimes hold credentials. **[docs]** "Built-in toolsets are read-only by default, respecting existing platform permissions… gated by the credentials you grant them" ([`why-holmesgpt.md`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/docs/why-holmesgpt.md)); "By design, HolmesGPT has read-only access and respects RBAC permissions" (README).
- **Bash allowlist second.** **[code]** Source: [`bash/`](https://github.com/robusta-dev/holmesgpt/tree/5feabfca750b/holmes/plugins/toolsets/bash).
  - The model must declare one prefix per pipeline segment. Commands are parsed with tree-sitter.
  - `CORE_ALLOW_LIST` covers `kubectl get/describe/logs/top/events/explain/diff/auth can-i/config view`, `jq`, `grep`, `head`, `tail`, `sort`, `uniq`, `wc`, `cut`, `tr`, `echo`, and a few system-info commands. `EXTENDED_ALLOW_LIST`, which **is the Helm default**, adds `cat`, `base64`, `ls`, `find`, `stat`, `du`, and `df` ([`default_lists.py`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/holmes/plugins/toolsets/bash/common/default_lists.py)).
  - `sudo` and `su` are always blocked (`HARDCODED_BLOCKS`). Argv checks deny `find -exec/-delete/-fprint`, `sort -o/--compress-program`, `uniq` output files, and write redirections ([`command_arg_rules.py`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/holmes/plugins/toolsets/bash/command_arg_rules.py), [`validation.py`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/holmes/plugins/toolsets/bash/validation.py)).
  - Loops, conditionals, `$(...)`, and anything not on the allowlist return `APPROVAL_REQUIRED` and wait for a human. The CLI has `--bash-always-allow`.
- **Gaps in the allowlist.** **[inferred]**
  - Nothing in `validation.py` stops `echo $SOME_API_KEY`: `echo` is allowlisted, and [`bash_instructions.jinja2`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/holmes/plugins/toolsets/bash/bash_instructions.jinja2) says "environment variable references are auto-approved". The chart mounts LLM API keys as env vars (`extraEnvVarsSecrets`, [`helm-configuration.md`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/docs/reference/helm-configuration.md)).
  - With the Helm-default extended list, `cat /var/run/secrets/kubernetes.io/serviceaccount/token` also has no path rule in the bash toolset.

  These paths were found by reading the code, not by running it, but they show that an allowlist on command names is not a secrets boundary.
- **Writes exist, but in a separate pod.** **[code]** The opt-in `kubernetesRemediation` MCP add-on runs with its own ServiceAccount and write RBAC.
  - It allows `edit, patch, delete, scale, rollout, drain, exec…` (`allowedCommands`).
  - Holmes marks `run_kubectl_command` as `approvalRequiredTools`, and bearer-token auth protects the HTTP endpoint.
  - The auto-approved diagnostic tools carry a target policy and a file-read path policy, written explicitly against prompt injection ("prompt-injected agent output could point curl at the cloud metadata service", `values.yaml` around lines 776–830).

  This is credential separation, but the LLM still chooses free-form commands and a human approves them.

### 7. Evidence references and untrusted-data framing

- **Tool results are raw `role: tool` messages.** **[code]** Each starts with `tool_call_metadata={"tool_name", "tool_call_id"}` and "Params used for the tool call: …" ([`holmes/core/models.py`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/holmes/core/models.py) `format_tool_result_data`). There is no delimiter, no "this is untrusted data" marker, and no injection instruction in the prompts.
- **The answer does not cite tool calls.** **[code]** The system prompt says: "Do not say 'based on the tool output' or explicitly refer to tools at all." The answer is free Markdown. `LLMResult.tool_calls` is returned *alongside* it, so a UI can show the calls, but nothing links a claim to a call ([`tool_calling_llm.py`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/holmes/core/tool_calling_llm.py)).
- **Evidence discipline lives in the prompt instead.** **[code]** "Trace each claim to specific tool output and hedge anything unverified". "Name an entity as affected only when you observed evidence for THAT entity". Impact is sorted into Affected / Checked healthy / Changed for another reason / Not checked, and every Affected line must quote a reason token such as `OOMKilled` or `Evicted` (`generic_ask.jinja2`).
- **Prompt-injection mitigations are structural.** **[code]** Tool parameters are `shlex.quote`d. `request_context` values with shell metacharacters are rejected outright (`reject_shell_metacharacters`, ROB-1104). The remediation add-on has target and path policies. None of these covers text inside tool output steering the model.

### 8. Remote and multi-cluster reach

- **One Holmes per cluster, outbound only.** **[docs]** In the Robusta product, "HolmesGPT runs as part of the in-cluster Agent", "SaaS connectivity is outbound-only — no inbound access is required", and "the Robusta Platform never connects to your data sources directly" ([Robusta architecture](https://docs.robusta.dev/master/how-it-works/architecture.html), fetched 2026-10-18).
- **Cross-cluster tools.** **[code]** Source: [`tool_call_worker.py`](https://github.com/robusta-dev/holmesgpt/blob/5feabfca750b/holmes/core/conversations_worker/tool_call_worker.py); design doc in the closed relay repo.
  - **Flow:** the caller's LLM calls a tool through relay's `platform-mcp`. Relay writes a row to a `RemoteToolCalls` table. The executor Holmes in the target cluster claims rows over its outbound Supabase connection and runs **exactly one tool per row, with no LLM loop**.
  - **Checks before running:** the caller and executor versions must be identical, so the schemas match. The toolset must not be internal (`is_core`) and must be `expose_remotely`. The `instance` must be one that is exposed. These checks are repeated here as defence in depth on top of filtering at publish time.
  - **Result:** capped at 1 MB.
- **What is exposed by default.** **[docs]** Only toolsets "useful exclusively inside a cluster": `kubernetes/core`, `kubernetes/logs`, and in-cluster Prometheus, with locality decided per instance from the URL. "Location-agnostic toolsets (… Datadog …) are not exposed by default: the caller can query those directly".
- **Docs and code disagree on remote approval.** The docs say remote `bash` runs pre-approved commands only and "any tool that would require approval is denied". The code returns `APPROVAL_REQUIRED` to the caller and honours a `remote_tool_approved` flag in the row metadata. What relay does with that flag cannot be checked, because relay is closed source.
- **The remote executor is not LLM-free.** **[code]** The executor builds `ToolInvokeContext(llm=self._get_llm(), …)`, so `llm_summarize` transformers on the remote side call an LLM.

## What incident-copilot should borrow / reject

| Q | Our proposal | What HolmesGPT does | Borrow | Reject | ADR 0001 impact |
|---|---|---|---|---|---|
| **Q1** Tool shape | Capability-level, Target-scoped tools instead of backend-specific queries | Mostly backend-specific (PromQL, LogQL, kind+jq) plus free-form `bash`. One capability-level tool, `fetch_pod_logs` | Typed parameter schemas. The `fetch_pod_logs` shape (time window, include and exclude regex, limit) as the model for `search_logs`. Hints in errors ("use `topk`", "narrow the query") | `bash` and operator-authored shell-template tools. Raw query languages as the main interface. If a raw PromQL escape hatch is ever added, the Sensor must inject the Target's label matchers and enforce the budget | **Tighten.** D1 forbids shell commands for *actions* only. Add to invariant 3 (or a new ADR) that investigation tools are typed queries with no shell or `exec`. HolmesGPT shows why: its allowlist leaks env vars and files (§6). Strengthens, does not weaken |
| **Q2** Read scope | Target only, same Location, or anything | Anything the credential allows (cluster-wide by default). Namespace scope is RBAC plus prompt text. Provenance is labelled per finding | **Same Location**, with the Target as the default anchor of every tool: parameters default to the Target, and other workloads in that Location are allowed by name. Target-only would make the M5.4 decoy unsolvable, because the model must read the `inventory` deploy to clear it. Carry `Location` and the workload in every evidence ref, as HolmesGPT's "real cluster of origin" rule does | "Anything": cross-Location reads should go through that Location's Sensor, never through one credential that spans Locations | **None.** Invariant 4 binds *actions*, not reads. Keep it that way, and do not extend it to reads. Wider reads do not weaken it, because `Decide` caps every off-Target Proposal at L1 |
| **Q3** Catalog | Owned by the core, filtered per Incident by capabilities the Sensor advertises | Owned by the operator, fixed per instance, filtered by config, prerequisites, and tags. Disabled and FAILED toolsets are listed in the prompt. MCP `allowed_tools`. Startup health-check tool | Prerequisites and health status per capability. Listing missing or failed capabilities to the model so the RCA says "no log backend in Location X" instead of guessing. The remote worker's **re-check at call time** (tool exposed, version or schema matches): the Sensor rejects any query for a capability it did not advertise | Operator-authored tools in the core catalog. A catalog that is the same for every investigation | **None.** This is invariant 8 in practice: an unknown, failed, or unadvertised capability is not offered, and if called it errors |
| **Q4** MCP | Only as a client adapter in the Control plane. No MCP server facing outward | Client only in the OSS code. Annotations ignored, `allowed_tools` used. The outward server is a SaaS feature (`platform-mcp`) behind a default-off switch, per-cluster RBAC, and pre-approved tools only | Client with an explicit `allowed_tools` list, a health check, and no trust in annotations. MCP servers in their own Deployment with their own ServiceAccount (the chart's `mcp-servers/` pattern) | An outward MCP server. HolmesGPT's needs three extra gates just to be safe, and it turns Sensors into a fleet-wide query API for any key holder | **None.** Note: the earlier research ([observability-mcp-ecosystem](https://github.com/itsankoff/incident-copilot/blob/research/observability-mcp-ecosystem/docs/research/observability-mcp-ecosystem.md)) assumed "our own MCP server stays". Q4 reverses that, so the README goal needs updating, not the ADR |
| **Q5** Redaction and budget | At the fetching edge (Sensor) plus a second pass in the Control plane | **No output redaction.** Token budget per tool: `min(15% of window, 25k)`. Spill to disk. Log truncation keeps the tail. A 1 MB cap at the remote edge. LLM summariser and compaction | Two budget layers, as HolmesGPT has (1 MB at the remote edge, a token cap in the loop): Sensor bytes plus a Control-plane cap relative to the window, `min(pct, absolute)`. Truncate oldest lines first with an explicit marker. "Narrow the query" errors instead of silent cuts. Refuse identical repeat calls | No redaction (fails invariant 7). Spill to disk with `cat` (needs a file or shell tool). `llm_summarize` on **raw** output: that sends unredacted data to a second model. Any summariser must run in the Control plane, *after* redaction | **Tighten wording.** D7 says redaction happens before data reaches "the LLM". Make it "any LLM call, including summarisation or compaction". HolmesGPT's remote executor also calls an LLM, which CONTEXT.md already forbids for Sensors. Keep that rule |
| **Q6** Read-only | Credentials first, allowlist second, tests third | The same order in practice: a get/list/watch ClusterRole without Secrets, then the bash allowlist, then human approval. Writes only in a separate remediation pod with its own ServiceAccount | The order. Shipping RBAC as the primary control. A separate ServiceAccount and pod for anything that writes. Also **leave `configmaps` out of the Sensor's RBAC, or redact them**, since HolmesGPT grants them. Add an RBAC test that the Sensor and Control plane cannot `get secrets` and cannot `create pods/exec` | The remediation add-on's model: the LLM picks free-form `kubectl` writes and a human approves. That breaks invariant 1 for us | **Wording only.** D4 still names "Agent" with Kubernetes RBAC. Split it into the Control plane (no write credentials, no per-Location Kubernetes credentials) and the Sensor (get/list/watch, no Secrets). This is a terminology supersede that does not weaken invariant 3 |
| **Q7** Citations and framing | The RCA cites evidence refs. Tool output is framed as untrusted | No citations: "do not … refer to tools at all". The `tool_call_id` is in each result header. No untrusted framing. Strong evidence discipline in the prompt (quote reason tokens, Affected / Checked / Not checked) | Put a stable evidence ref (the `tool_call_id` equivalent plus Location and Target) in each result header, and require the RCA schema to cite refs per claim. Copy the four-bucket impact rule and the "quote the reason token" rule into the RCA prompt. Optionally validate that every cited ref exists in the audit log | The "don't refer to tools" style rule | **None.** Framing is a hint, not a control (ADR force 2). The controls remain D1 to D3 |

### Places where HolmesGPT argues for superseding ADR 0001

1. **Invariant 7 → "Secrets are not readable by RBAC" instead of "never reach the LLM".** HolmesGPT's approach is RBAC-only. Rejected, because it **would weaken** the invariant: §6 shows env vars, mounted tokens, and ConfigMaps still reaching the model. Keep redaction as the control and RBAC as defence in depth.
2. **Invariant 3 → let the edge component (the Sensor) call an LLM to summarise.** HolmesGPT's remote executor does this. Rejected, because it **would weaken** the invariant: an LLM would read unredacted data and run next to Location credentials. Summarisation, if wanted, belongs in the Control plane after redaction.
3. **Invariant 3 → allow a shell tool restricted by an allowlist for investigation.** Rejected, and the ADR should say so explicitly. Today's wording ("investigation tools are read-only") would technically allow it. **Tightening, not weakening.**
4. **D4 terminology (Agent → Control plane plus Sensor).** HolmesGPT has nothing to say here, but the topology from #8 already outdates D4. A supersede that only renames and splits the roles **does not weaken** invariant 3, as long as the Control plane holds no write credentials and the Sensor holds only get/list/watch.

Invariants 4 and 8 need no change. HolmesGPT's practice (fail the toolset on a prerequisite timeout, re-check exposure at call time) is consistent with them.
