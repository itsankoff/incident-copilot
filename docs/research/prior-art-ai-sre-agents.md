# Prior art: how existing AI SRE agents model platforms, signals, and actions

- **Ticket:** #4 (Wayfinder map #3)
- **Date:** 2026-10-17. All sources were read on this date. These products change monthly, so re-check before quoting a detail in an ADR.
- **Question:** How do HolmesGPT/Robusta, k8sgpt, Azure SRE Agent, AWS DevOps Agent, and Komodor Klaudia model (a) the platforms they cover and how they add new ones, (b) what triggers an investigation, (c) how investigation tools are packaged, and (d) what actions they may take and how those are gated? Where does incident-copilot genuinely differ, and what should it adopt or deliberately avoid?

Sources are primary: official docs and source repositories. Vocabulary follows `CONTEXT.md` (Signal, Alert, Detector, Runbook, Proposal, Autonomy level, Executor, Install).

## Summary

1. **Nobody models "a platform" as a first-class type.** Every product has two separate things: a **target model** (Kubernetes kinds, Azure resource types, an AWS topology graph) and **bundles of tools**. A new platform arrives as a new tool bundle, almost always over MCP, plus credentials. The coupling between "this platform's targets" and "this platform's actions" is implicit everywhere.
2. **Triggers converge on what `CONTEXT.md` already calls Signal = Alert + Detector.** Alert ingestion from existing monitoring (Alertmanager, PagerDuty, ServiceNow, Datadog, webhooks) is universal. Built-in detection exists in the Kubernetes-native tools (k8sgpt analyzers, Komodor, Robusta triggers). AWS adds an explicit **triage stage** (link to an existing investigation, skip, or proceed) before investigating.
3. **Investigation tools are packaged as MCP servers or declarative toolsets**, and the main classification is read vs. write. Several products **fail open** on that classification (AWS treats unclassified MCP tools as `READ_ONLY`; Azure hooks default to `failMode: allow`).
4. **Write actions are gated in one of three ways:** (i) free-form commands filtered by allow/deny patterns plus human approval (HolmesGPT, Azure, Komodor `RunKubectl`); (ii) a whitelist of predefined actions with a policy scope (Komodor self-healing, k8sgpt-operator); (iii) human approval for every action, with no autonomy at all (AWS directed actions).
5. **Where incident-copilot is genuinely different:** a closed, typed Runbook registry, a per-Runbook *and* per-environment autonomy ladder computed as a downgrade-only `min()`, an Executor process that never calls an LLM, approval bound to a digest of the target's spec generation and the dry-run result, scope binding to the alerting workload, and autonomy promotion gated on eval evidence. No product reviewed has the last two, and only k8sgpt-operator (alpha) comes close to the Executor split.
6. **Correction to ADR 0001's prior-art note:** Azure SRE Agent no longer has agent-wide *ReadOnly / Review / Autonomous* modes. Run modes are now **Review** and **Autonomous**, set **per response plan and per scheduled task**, with an agent-level default as fallback. Read-only operation now comes from the *Reader* permission level. Review mode gates only Azure infrastructure writes. ([run modes](https://learn.microsoft.com/azure/sre-agent/run-modes), [permissions](https://learn.microsoft.com/azure/sre-agent/permissions))

## Per product

### HolmesGPT (CNCF sandbox) and Robusta

**(a) Platforms.** HolmesGPT has no platform type. Everything, Kubernetes included, is a **toolset**. Built-in toolsets live in `holmes/plugins/toolsets/` as YAML (`kubernetes.yaml`, `aks.yaml`, `argocd.yaml`, `helm.yaml`, `openshift.yaml`, …) or Python packages (`prometheus/`, `datadog/`, `database/`, `mcp/`, …). ([source tree](https://github.com/HolmesGPT/holmesgpt/tree/master/holmes/plugins/toolsets), [built-in toolsets](https://holmesgpt.dev/data-sources/builtin-toolsets/)) A toolset declares `prerequisites` (env vars present, or a command exits 0, e.g. `kubectl version --client`), and is enabled only when they pass. Tags (`core`, `cli`, `cluster`) decide where it loads. ([custom toolsets doc](https://github.com/HolmesGPT/holmesgpt/blob/master/docs/data-sources/custom-toolsets.md)) A new platform is added as a custom YAML toolset, an API toolset, or a remote MCP server.

**(b) Triggers.** Alert sources implement a small `SourcePlugin` interface (`fetch_issues`, `fetch_issue`, optional `stream_issues`, optional `write_back_result`) that yields a source-neutral `Issue` (`id`, `name`, `source_type`, `source_instance_id`, `url`, `raw`, …). Sources exist for Prometheus/Alertmanager, PagerDuty, OpsGenie, Jira, and GitHub. ([interfaces.py](https://github.com/HolmesGPT/holmesgpt/blob/master/holmes/plugins/interfaces.py), [issue.py](https://github.com/HolmesGPT/holmesgpt/blob/master/holmes/core/issue.py), [sources](https://github.com/HolmesGPT/holmesgpt/tree/master/holmes/plugins/sources)) The Holmes Operator adds a `HealthCheck` CRD: a **natural-language query** that an LLM answers with pass/fail, optionally alerting a destination. ([health checks](https://github.com/HolmesGPT/holmesgpt/blob/master/docs/operator/health-checks.md)) Robusta playbooks pair a trigger (`on_prometheus_alert`, `on_pod_crash_loop`, `on_deployment_update`, `on_kubernetes_warning_event_create`, …) with actions. ([Robusta playbooks](https://docs.robusta.dev/master/playbook-reference/index.html))

**(c) Tool packaging.** A custom tool is a shell `command` template. `{{ var }}` is filled in by the LLM, and `${ENV}` is hidden from it. Parameters are optional and "usually inferred". Built-in tools add structured parameters and output transformers (e.g. `llm_summarize`). ([custom toolsets doc](https://github.com/HolmesGPT/holmesgpt/blob/master/docs/data-sources/custom-toolsets.md), [kubernetes.yaml](https://github.com/HolmesGPT/holmesgpt/blob/master/holmes/plugins/toolsets/kubernetes.yaml)) HolmesGPT has an eval suite of 150+ LLM scenarios. It uses the suite to benchmark models and to run regression tests, not to gate autonomy. ([evaluations](https://github.com/HolmesGPT/holmesgpt/blob/master/docs/development/evaluations/index.md))

**(d) Actions and gating.** Holmes is read-only by default. Writing is opt-in through the **Kubernetes Remediation MCP server**, a separate pod with its own scoped ClusterRole (not `cluster-admin`, no `secrets`) and an ingress-only NetworkPolicy. Each tool is fixed as either auto-approved or human-approved: read-only diagnostics run immediately, and the catch-all `run_kubectl_command` (all mutations, arbitrary exec) requires human approval. It is restricted by a verb allowlist (`edit,patch,delete,scale,rollout,cordon,uncordon,drain,taint,label,annotate,run,exec`) and a flag blocklist (`--kubeconfig`, `--context`, `--token`, `--as`, …), and it can be disabled with `allowArbitraryKubectlCommands: false`. ([remediation MCP](https://github.com/HolmesGPT/holmesgpt/blob/master/docs/data-sources/builtin-toolsets/kubernetes-remediation-mcp.md)) The same doc admits that an auto-approved diagnostic probe could be steered by injected text "in an alert description" toward cloud metadata endpoints. Holmes added a default in-cluster-only target policy for that reason. The bash toolset approves commands by **prefix**, and its own docs warn that "a prefix does not restrict where a command goes". ([bash toolset](https://github.com/HolmesGPT/holmesgpt/blob/master/docs/data-sources/builtin-toolsets/bash.md)) Robusta's remediation actions (for example `alert_handling_job`, which runs a Kubernetes Job) run **automatically on trigger**, with no approval step documented. They are deterministic playbooks, not LLM choices. ([Robusta job remediation](https://docs.robusta.dev/master/playbook-reference/automatic-remediation-examples/job-to-remediate-alert.html))

### k8sgpt and k8sgpt-operator (CNCF sandbox)

**(a) Platforms.** k8sgpt is Kubernetes only, and its unit of coverage is the **Kubernetes kind**. Each analyzer implements `IAnalyzer.Analyze(Analyzer) ([]Result, error)`, and a `Result` is `{Kind, Name, Error []Failure, Details, ParentObject}`. ([types.go](https://github.com/k8sgpt-ai/k8sgpt/blob/main/pkg/common/types.go), [analyzers](https://github.com/k8sgpt-ai/k8sgpt/tree/main/pkg/analyzer)) "Integrations" (`aws`/EKS, `keda`, `kyverno`, `prometheus`) implement `IIntegration`, which can `Deploy`/`UnDeploy` into the cluster and **adds analyzers** (`AddAnalyzer`, `OwnsAnalyzer`). ([integration.go](https://github.com/k8sgpt-ai/k8sgpt/blob/main/pkg/integration/integration.go)) Third-party analyzers run as gRPC services against a published protobuf schema (`custom_analyzers`). ([README](https://github.com/k8sgpt-ai/k8sgpt))

**(b) Triggers.** There is no alert ingestion. The analyzers are deterministic **detectors** that run on demand (`k8sgpt analyze`) or on a schedule in the operator (`analysis.interval`). The LLM only explains a finding (`--explain`). ([README](https://github.com/k8sgpt-ai/k8sgpt), [operator](https://github.com/k8sgpt-ai/k8sgpt-operator))

**(c) Tool packaging.** Analyzers are compiled Go. k8sgpt also serves gRPC (`k8sgpt serve`) and MCP (`k8sgpt serve --mcp`) so other agents can use it as a tool server. It can anonymise data before it reaches the LLM (`--anonymize`), but the README says event messages are not masked. ([README](https://github.com/k8sgpt-ai/k8sgpt))

**(d) Actions and gating.** The operator has **alpha auto-remediation** that is "deny-by-default". This is the closest design to ADR 0001 found in this survey. ([AUTO_REMEDIATION.md](https://github.com/k8sgpt-ai/k8sgpt-operator/blob/main/AUTO_REMEDIATION.md))
- The LLM is "asked only for an existing container name and a replacement image". The operator builds the candidate manifest itself.
- A `resources` allowlist of GVKs lets the operator *propose*. Execution also needs a **registered per-GVK policy**, and today the only policies are single-path container-image replacements. Other standard resources need an object-local opt-in annotation listing exact JSON Pointer paths.
- Before executing, the operator re-fetches the target and requires the same UID and `resourceVersion`, exactly one changed path, a server-side dry run, and a `resourceVersion` test in the real patch.
- Pod findings are resolved to their owning workload (`Pod → ReplicaSet → Deployment`), so the change goes into desired state rather than an ephemeral Pod. Results carry an exact `targetRef` (`apiVersion, kind, namespace, name, uid, resourceVersion`).
- Each proposal and its lifecycle are recorded as a `Mutation` CR.
- Stated gaps: there is no human-approval or proposal-only mode yet, no full audit, no rollback, and `similarityRequirement` "no longer authorizes execution" because "whole-manifest textual similarity is not a safety proof".

### Azure SRE Agent

**(a) Platforms.** Azure is native. Through its managed identity the agent queries Azure Monitor, Application Insights, Log Analytics, and Resource Graph, uses ARM and the Azure CLI on "any Azure resource type", and runs kubectl diagnostics on AKS. Anything outside Azure arrives through **connectors**: Kusto, GitHub, Azure DevOps, Teams, Outlook, and generic **MCP servers** (Datadog, Splunk, New Relic, Dynatrace, …). Admins can scope tools to **custom agents** (subagents), for example with `mcp_tools: [connection-id/*]`. ([connectors](https://learn.microsoft.com/azure/sre-agent/connectors))

**(b) Triggers.** One **incident platform** can be active at a time: PagerDuty, ServiceNow, or Azure Monitor. **Response plans** filter incidents (by severity, service, priority, or title) and route them to a custom agent. **Scheduled tasks** run checks on a schedule. ([response plan](https://learn.microsoft.com/azure/sre-agent/response-plan), [incident platforms](https://learn.microsoft.com/azure/sre-agent/incident-platforms))

**(c) Tool packaging.** The agent has built-in typed tool families such as `RunAzCliReadCommands`, `RunAzCliWriteCommands`, `RunKubectlReadCommand`, `RunKubectlWriteCommand`, `ExecutePythonCode`, and `RunShellCommand`, plus MCP tools. ([tool access policies](https://learn.microsoft.com/azure/sre-agent/tool-access-policies))

**(d) Actions and gating.** Several layers, from highest to lowest precedence ([tool access policies](https://learn.microsoft.com/azure/sre-agent/tool-access-policies)):
1. **Hooks** come first. `PostToolUse` and `Stop` hooks are either *prompt* hooks (an LLM judge) or *command* hooks (scripts), with `failMode` defaulting to `allow`. A **user-defined hook returning allow overrides even a global deny**. ([hooks](https://learn.microsoft.com/azure/sre-agent/agent-hooks))
2. **Tool access policies** are globs on tool names and arguments, for example `RunKubectlWriteCommand(kubectl delete *)`. Only the global scope can deny. Custom-agent and thread scopes can only add allows, and "allow takes priority" over ask.
3. Connector-level `RequiresApproval`.
4. **Run modes**: *Review* (the default for a new agent) or *Autonomous* (the default for a new response plan or scheduled task). They are set per response plan and per task. Review shows Approve/Deny **only for Azure infrastructure writes**; other actions, like posting to Teams, "proceed based on the agent's reasoning". Only *SRE Agent Administrators* can approve. Microsoft's guidance is to watch Review mode for 2–4 weeks and then switch the triggers you always approve to Autonomous. ([run modes](https://learn.microsoft.com/azure/sre-agent/run-modes))

Underneath all of this is Azure RBAC on a user-assigned managed identity, at the *Reader* or *Privileged* level per resource group. When the identity lacks a permission, the agent asks an administrator to lend theirs through Entra on-behalf-of. ([permissions](https://learn.microsoft.com/azure/sre-agent/permissions))

### AWS DevOps Agent

**(a) Platforms.** An **Agent Space** is the boundary: the AWS accounts (one primary and several secondary), third-party integrations, and users it may access. AWS recommends separate Spaces for production and non-production. ([Agent Spaces](https://docs.aws.amazon.com/devopsagent/latest/userguide/about-aws-devops-agent-what-are-devops-agent-spaces.html)) The agent builds a **topology** automatically from CloudFormation stacks and Resource Explorer tags, and links it to CI/CD. Investigations may still go beyond the topology. ([topology](https://docs.aws.amazon.com/devopsagent/latest/userguide/about-aws-devops-agent-what-is-a-devops-agent-topology.html)) Other platforms arrive as integrations: EKS access, Azure resources, Azure DevOps, GitHub, GitLab, Datadog, Dynatrace, Grafana, New Relic, Splunk, MCP servers, and remote A2A agents. ([docs TOC](https://docs.aws.amazon.com/devopsagent/latest/userguide/toc-contents.json)) Knowledge is packaged as **Skills**: `SKILL.md` directories that follow a subset of the Agent Skills spec, are targeted at agent types (Incident Triage, Incident RCA, Incident Mitigation, …), and are non-executable unless the Sandbox is enabled. ([skills](https://docs.aws.amazon.com/devopsagent/latest/userguide/about-aws-devops-agent-devops-agent-skills.html))

**(b) Triggers.** Investigations start from built-in integrations (for example ServiceNow tickets), **webhooks** (integration-specific, or generic with HMAC signing plus timestamp replay protection, or a bearer token), or by hand. A **triage stage** comes first. It correlates a new incident with active investigations in a look-back window ("typically 20 minutes") and decides *Linked* (sent as a steering message to the existing investigation), *Skipped* (it matched skip criteria in a skill), or *Proceed*. Operators can unlink or unskip. ([incident response](https://docs.aws.amazon.com/devopsagent/latest/userguide/production-operations-autonomous-incident-response.html), [webhooks](https://docs.aws.amazon.com/devopsagent/latest/userguide/configuring-integrations-and-knowledge-invoking-devops-agent-through-webhook.html)) After an investigation, a human can mark the RCA correct or incorrect. An incorrect verdict becomes a "reflections" memory, and the verdicts give an accuracy metric.

**(c) Tool packaging.** Built-in AWS SDK access plus integration and MCP tools. Each MCP tool is classified `READ_ONLY`, `MUTATIVE`, or `DESTRUCTIVE`. **A tool without a classification defaults to `READ_ONLY`**, and an association registered through the API without `toolDetails` treats *every* tool as read-only. ([directed actions](https://docs.aws.amazon.com/devopsagent/latest/userguide/working-with-devops-agent-working-with-directed-actions.html))

**(d) Actions and gating.** "Directed actions" are **never autonomous** ([directed actions](https://docs.aws.amazon.com/devopsagent/latest/userguide/working-with-devops-agent-working-with-directed-actions.html)):
- They are off by default. Turning them on takes layered opt-in: an Agent Space toggle (`elevatedActionsEnabled`), a per-account **elevated IAM role** (the "ceiling", not a standing grant), and per-tool classification or `enabledElevatedTools`.
- Every action needs operator approval **in chat**. The approval covers the specific tool, operation, and resource, and it is valid for a bounded window. A mutating call made outside chat, such as during an autonomous investigation, *fails* instead of asking.
- Credentials for an approved action carry a **session policy scoped to that one operation and resource**, built only from a curated list of IAM actions. CloudTrail records the approving operator as the source identity.
- Some guardrails hold whatever the permissions say and approval cannot override them: no delete-class operations, no changes to IAM permissions boundaries, and no `iam:PassRole` by default. Tools classified `DESTRUCTIVE` are never invoked.
- Mitigation proposals appear inline after the RCA. Each describes the action, the expected outcome, and its prerequisites, and the operator can adjust the parameters before applying.

### Komodor Klaudia

**(a) Platforms.** Klaudia is Kubernetes-native, with a broad resource model: workloads, storage, configuration, networking and RBAC objects, add-ons (Argo CD, Helm, cert-manager, external-dns, autoscalers), CRDs, and ML/workflow systems (Argo Workflows, Argo Rollouts, Airflow, Spark). Workflow failures are correlated into one RCA. ([How Klaudia Investigates](https://help.komodor.com/hc/en-us/articles/36194433294482)) Non-Kubernetes sources come in as category integrations (cloud provider, APM, CI, databases, queues, alert systems) and **generic MCP**. ([Generic MCP](https://help.komodor.com/hc/en-us/articles/33108104322962))

**(b) Triggers.** Komodor's in-cluster agent detects failures itself (CrashLoopBackOff, OOMKill, scheduling failures, readiness failures, failed deploys) and investigates "without requiring manual setup or steering". Chat and Slack are also entry points. ([How Klaudia Investigates](https://help.komodor.com/hc/en-us/articles/36194433294482))

**(c) Tool packaging.** Built-in investigation tools per category, generic MCP, and organisational knowledge (`Klaudia.md`, knowledge-base integration). ([Klaudia.md](https://help.komodor.com/hc/en-us/articles/32463600112786), [knowledge base](https://help.komodor.com/hc/en-us/articles/28686161842834))

**(d) Actions and gating.** There are four tiers: a copy-paste command, a guided suggestion, a **one-click "Run"** in the UI, and **autonomous self-healing**. Self-healing runs only actions on a **whitelist** ("scaling, restarting, or rolling back"; for example `helm rollback`, *Restart Deployment*, rerun a Job). It needs a **policy** scoped to a cluster, with namespaces and allowed actions, and **each cluster can have only one policy**. Actions run with platform RBAC credentials and are all audited. Fixes that need several commands are downgraded to a suggestion. ([Self-Healing](https://help.komodor.com/hc/en-us/articles/32313630528786)) Separately, **RunKubectlCommand** (admins only) lets Klaudia "suggest and execute any kubectl command", gated only by user confirmation in the one-click flow. ([RunKubectl](https://help.komodor.com/hc/en-us/articles/33573756614290))

### Not covered

Datadog Bits AI SRE, PagerDuty's agents, incident.io, Resolve.ai, and Cleric were not researched in depth. Their public docs are either overview-level or behind login (the Bits AI SRE overview page does not document triggers or actions: [docs](https://docs.datadoghq.com/bits_ai/bits_ai_sre/)).

## Where incident-copilot genuinely differs

1. **Autonomy is set per action and per environment, computed downward, and the model can only lower it.** Azure sets it per response plan, Komodor per cluster policy, and AWS never grants it. No product combines a per-action maximum, an environment ceiling, a kill switch, and guard caps in one pure, explained `min()`.
2. **The Executor never calls an LLM, and it re-validates everything.** Holmes's remediation MCP server is a separate process, but it executes model-written kubectl. k8sgpt-operator is the only other design where the model's output is reduced to data and the controller builds the change. Its executor still lives in the operator that also calls the LLM.
3. **Approvals are bound to a digest that includes the target's `generation` and the dry-run result, and expiry counts as a denial.** AWS binds an approval to a tool, operation, and resource for a time window. k8sgpt uses a `resourceVersion` test but has no human approval yet. Nobody else binds the approval to the dry-run result.
4. **Scope binding to the alerting workload.** Every other scope reviewed is static: an Agent Space, an RBAC role, a cluster policy, a response-plan filter. None caps actions on workloads the triggering Signal did not name. This is what defeats injected "roll back payments-api" text.
5. **Promotion to autonomy needs eval evidence, including an unsafe-action rate.** HolmesGPT has a large eval suite, but it benchmarks models. AWS collects RCA accuracy from user feedback. Azure recommends watching for 2–4 weeks. None ties promotion to a measured threshold.

**Not a differentiator (table stakes):** MCP-exposed read tools, alert webhooks, an RCA written into a ticket, read-only investigation by default, RBAC least privilege, and an audit trail. Ship them, but do not pitch them.

## Adopt

- **A source-neutral Signal with a small source interface.** HolmesGPT's `SourcePlugin` (`fetch`, `stream`, `write_back_result`) and `Issue` are almost exactly the Alert side of `CONTEXT.md`'s Signal. `write_back_result` is the shape of the ticketing adapter.
- **A triage stage before investigation:** link to an open incident, skip, or proceed, within a look-back window. This is AWS's model, and it is the natural place for "re-investigation on re-fire" and for de-duplicating an Alert and a Detector that fire on the same failure. Keep the correlation rule deterministic (same Install, same target, same window) rather than AI-judged.
- **Exact target identity and owner resolution as part of each platform.** k8sgpt's `targetRef` (`apiVersion, kind, namespace, name, uid, resourceVersion`) and its `Pod → ReplicaSet → Deployment` resolution are the Kubernetes instance of what every platform needs to provide: a typed Target, how to resolve the target named by a Signal, and the version field the approval digest pins.
- **Per-action, short-lived credentials for cloud Runbooks.** AWS's elevated role (the ceiling) plus a session policy scoped to the approved operation fits our Executor directly. For a future ECS or Lambda Runbook, the Executor should assume a role whose session policy allows only that Runbook's API calls on that target. Azure's equivalent is a narrowly scoped role assignment. Cloud IAM then becomes the ceiling, not the allowlist, as ADR 0001 already argues for Kubernetes RBAC.
- **Signed Signal ingestion.** Use HMAC over the timestamp and payload, with replay protection, for generic webhooks (AWS's model). Alertmanager cannot sign its webhooks, so terminate them with a bearer secret on a NetworkPolicy-restricted path.
- **Tool prerequisites.** HolmesGPT enables a toolset only when its backend is configured and reachable. A platform bundle should declare the same thing, so an Install without Loki has no log tool rather than one that fails mid-investigation.
- **Egress control on read-only tools.** Holmes's finding that injected alert text can steer an auto-approved *read-only* probe to cloud metadata endpoints applies to us too. Read-only does not mean harmless. Fixed backends per tool, plus a NetworkPolicy on the agent, belong in the M2 design.

## Avoid

- **Free-form command tools filtered by patterns.** These include Holmes's bash prefixes, Azure's `toolGlob(argGlob)`, and Komodor's `RunKubectlCommand`. The vendors' own docs show the limit: "a prefix does not restrict where a command goes". ADR 0001 D1 already excludes this. Keep it that way for cloud platforms, where "just run the CLI" is tempting.
- **LLM-judged safety controls.** Azure *prompt* hooks are a quality gate, not a safety control. Never put an LLM judge on the path to the Executor.
- **Fail-open defaults.** Examples: AWS treats unclassified MCP tools as read-only; Azure hooks default to `failMode: allow`; a new Azure response plan defaults to Autonomous; Azure Review mode gates only Azure infrastructure writes. In incident-copilot, every new seam (a platform bundle, a Signal source, an MCP tool) must default to the lowest level and to "unknown means not allowed".
- **Narrower scopes that can widen access.** Azure lets a thread-level allow skip approval, and a user hook's allow overrides a global deny. Keep ADR 0001's rule that every input can only lower the level, including per-platform configuration.
- **Natural-language health checks as Detectors.** Holmes's `HealthCheck` CRD turns an LLM answer into a pass or fail. Detectors must be deterministic rules (the k8sgpt and Komodor model), or a non-deterministic component starts incidents.
- **One autonomy setting per cluster or per agent.** Komodor allows one policy per cluster, and Azure sets an agent-wide default. Both are coarser than per Runbook × environment. ADR 0001 rejected this already, and the products confirm the tradeoff.

## Implications for the platform seam (map #3)

The products suggest that a **platform** in incident-copilot should be a bundle of five things that today's products keep separate. Keeping them together is what lets each ADR 0001 invariant hold on every platform.

1. **Target model:** typed Target identity, owner resolution, and the version field used in the approval digest (Kubernetes: GVK, namespace, name, UID, `generation`).
2. **Scope resolver:** maps a Signal's labels to "the alerting workload" on that platform (invariant 4).
3. **Read tools:** read-only MCP tools with declared prerequisites and fixed backends (invariant 3).
4. **Detectors:** deterministic rules that emit Signals.
5. **Runbooks:** typed parameters, preconditions, server-side dry run, verification, and per-action scoped write credentials that only the Executor holds (invariants 1, 3, 5).

Nothing in the products reviewed argues for relaxing an ADR 0001 invariant. The one prior-art note in ADR 0001 that is out of date (Azure's run modes) is a fact correction, not a design change.
